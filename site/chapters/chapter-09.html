M9 - Applied GPU Inference Capstone

A practical closing module that connects CUDA concepts to Python, PyTorch, vLLM, GPU memory behavior, inference throughput, latency, and cost estimation.

M8 PreviousM9

Learning outcomes

  • Connect low-level CUDA concepts to everyday Python and inference workflows.
  • Measure GPU usefulness with latency, throughput, memory use, and transfer overhead instead of intuition.
  • Explain why serving systems such as vLLM can outperform naive single-request inference loops.

Scope

This module is a capstone skeleton. It does not introduce a new CUDA programming model; it turns the previous modules into practical experiments for programmers who usually work with Python, PyTorch, and vLLM.

1. Capstone Topics

1.1 PyTorch benchmark: CPU versus GPU is not automatic

Build a Python experiment that compares small CPU operations, small GPU operations, large matrix multiplications, explicit tensor transfers, and timing with torch.cuda.synchronize(). The goal is to show when GPU execution helps and when launch overhead or transfer overhead dominates.

  • Compare CPU and GPU runtime across increasing tensor sizes.
  • Measure transfer cost separately from compute cost.
  • Explain the first problem size where GPU execution becomes worthwhile.

1.2 PyTorch memory lab: why VRAM disappears

Create a memory-focused script that allocates tensors of increasing size and observes torch.cuda.memory_allocated(), torch.cuda.memory_reserved(), tensor lifetime, batch-size limits, and out-of-memory behavior. The goal is to connect device memory capacity to real model and batch decisions.

  • Track allocated and reserved memory during tensor creation and deletion.
  • Find the maximum batch size for a simple workload.
  • Explain why freeing Python objects and releasing cached memory are different operations.

1.3 Mini inference benchmark with PyTorch

Run a small model or tensor workload in Python and compare CPU inference, GPU inference, and different batch sizes. Record latency, throughput, and GPU memory use so the result is framed as an engineering measurement rather than a generic speedup claim.

  • Test batch sizes such as 1, 8, 32, and 64.
  • Report latency per request and throughput per second.
  • Relate the measurements to launch overhead, parallelism, and memory pressure.

1.4 vLLM lab: serve a model through an OpenAI-compatible endpoint

Use vLLM to serve a small open model, call it from Python through an OpenAI-compatible client, then compare a single request with multiple concurrent requests. The goal is to show why a serving engine matters once inference becomes a shared workload.

  • Start a local vLLM server with a model that fits the available GPU.
  • Send requests from a Python client using the OpenAI-compatible API shape.
  • Observe tokens per second, request latency, GPU utilization, and VRAM use.

1.5 KV cache and context length experiment

Vary prompt length, generated-token count, and concurrency while observing memory use and throughput. The goal is to make the cost of long context and concurrent sessions concrete through the KV cache rather than treating context length as a free parameter.

  • Compare short prompts with long prompts on the same model.
  • Increase concurrent requests and watch memory growth.
  • Explain how context length, batch scheduling, and available VRAM constrain serving capacity.

1.6 Profiling workflow: from slow to explained

Profile one Python or inference workflow with host-side timers, GPU observation tools, and optionally Nsight Systems. The goal is to separate total application time, Python overhead, CUDA API activity, transfers, kernel work, GPU idle time, and serving-engine scheduling behavior.

  • Record end-to-end time from Python.
  • Observe GPU utilization and memory with command-line tools.
  • Identify whether the workload is limited by compute, memory, transfers, batching, or host-side overhead.

1.7 Cost per million tokens

Turn measured inference throughput into a simple cost model. Estimate cost per million tokens from GPU hourly price or local hardware cost, tokens per second, utilization, concurrency, and power assumptions. The goal is to connect performance measurement to deployment decisions.

  • Compute tokens per second from a measured run.
  • Estimate hourly token output under realistic utilization.
  • Compare local hardware, rented GPU inference, and managed API usage as separate operating models.

2. Suggested Final Sequence

2.1 Why GPU?

Start with a PyTorch CPU/GPU benchmark across increasing tensor sizes. This closes the loop on host/device execution, transfer overhead, launch overhead, and correct timing.

2.2 Why memory matters?

Move into VRAM, batch size, long context, and KV cache behavior. This connects the memory hierarchy and capacity discussion to the most common practical failure mode in inference work.

2.3 Why vLLM?

Finish by serving a model with vLLM, calling it from Python, measuring concurrency, latency, throughput, and memory, then estimating cost per million tokens. This makes the final artifact directly relevant to Python developers and LLM-serving workflows.
