M10 - CUDA and GPU Computing Glossary

A compact reference for the most important CUDA, PyTorch, GPU architecture, profiling, and inference terms used throughout the course.

Learning outcomes

  • Connect architecture terms to PyTorch and inference workflows.
  • Use consistent language when explaining measurements, bottlenecks, and optimization choices.

Scope

This final module is a glossary. It is meant as a practical lookup page, not as a replacement for the full module explanations and examples.

1. GPU Architecture and Execution

1.1 Host

The CPU side of a heterogeneous program. The host allocates data, launches GPU work, handles control flow, and receives results back from the device when needed.

1.2 Device

The GPU side of a CUDA program. Device memory and device execution are separate from ordinary CPU execution, even when a framework such as PyTorch hides much of the setup.

1.3 Kernel

A function scheduled for execution on the GPU by many threads. In CUDA C++, kernels are launched explicitly; in PyTorch, many tensor operations schedule GPU kernels internally.

1.4 Thread

The smallest programmed unit of CUDA work. Each thread usually handles one element or one small piece of a larger data-parallel problem.

1.5 Thread block

A group of CUDA threads that execute together on one Streaming Multiprocessor and can cooperate through shared memory and block-level synchronization.

1.6 Grid

The full collection of thread blocks launched for one CUDA kernel. The grid defines how a problem is divided into blocks and threads.

1.7 Warp

A hardware scheduling group of threads, commonly 32 threads on NVIDIA GPUs. Threads in a warp execute in lockstep for many instructions, so divergent control flow can reduce efficiency.

1.8 Streaming Multiprocessor

An SM is the GPU execution unit that schedules warps and provides execution lanes, registers, shared memory, and other local resources.

1.9 Occupancy

A measure of how many warps are resident on an SM compared with the maximum possible. Higher occupancy can help hide latency, but it is not the same thing as performance.

1.10 Divergence

A situation where threads in the same warp take different control-flow paths. The hardware may need to execute paths separately, reducing useful parallel work.

1.11 SIMD

Single Instruction, Multiple Data. A SIMD execution model applies one instruction to multiple data elements at the same time using vector lanes. The programmer typically thinks in terms of vector operations whose lanes follow the same instruction stream.

1.12 SIMT

Single Instruction, Multiple Threads. CUDA uses a SIMT model: many independent threads execute the same kernel and are scheduled in groups called warps. Threads have their own registers and logical control flow, but threads in one warp share instruction execution, so divergent branches can reduce efficiency. SIMT combines the programming model of independent threads with hardware execution that resembles SIMD at the warp level.

2. Memory and Data Movement

2.1 Global memory

The large device memory space accessible by GPU threads. It has high bandwidth but higher latency than on-chip resources, so access patterns matter.

2.2 Shared memory

Fast on-chip memory shared by threads in the same block. It is useful for data reuse, tiling, and reducing repeated global-memory traffic.

2.3 Register

Very fast per-thread storage. Using too many registers per thread can reduce occupancy because each SM has a limited register file.

2.4 Host-device transfer

A copy between CPU memory and GPU memory. Transfers can dominate runtime when the GPU computation is small or when data moves unnecessarily.

2.5 Pinned memory

Page-locked host memory that the operating system cannot freely move or page out. It can improve large transfers and is required for many effective asynchronous copy patterns.

2.6 CUDA stream

An ordered queue of CUDA operations. Work in one stream runs in order, while independent streams may allow overlap between copies and kernels when hardware and dependencies permit it.

2.7 Synchronization

A point where execution waits for previous work to complete. In PyTorch, synchronization can happen explicitly through CUDA APIs or implicitly when Python asks for a completed CPU-visible result.

2.8 Memory coalescing

An efficient access pattern where neighboring threads access neighboring memory locations, allowing the hardware to combine memory requests effectively.

3. Linear Algebra and Libraries

3.1 GEMM

General Matrix Multiply. GEMM is the operation family behind many dense linear algebra workloads, commonly written as matrix multiplication plus optional scaling and accumulation.

3.2 SGEMM

Single-precision GEMM. SGEMM performs GEMM using 32-bit floating-point values and is a common benchmark and building block for scientific computing and machine learning.

3.3 cuBLAS

NVIDIA's CUDA library for BLAS routines such as GEMM. It is usually the production choice for dense matrix multiplication instead of writing a custom teaching kernel.

3.4 cuDNN

NVIDIA's CUDA-X library for deep-learning primitives such as convolution, activation, normalization, pooling, and related forward or backward operations.

3.5 CUDA-X

A family of NVIDIA GPU-accelerated libraries built on CUDA. CUDA-X is not one library; it includes domain libraries for linear algebra, deep learning, signal processing, and more.

3.6 Tiling

An optimization technique that divides a problem into tiles so data can be reused from faster memory before loading the next tile.

4. PyTorch and Inference

4.1 Tensor

The central PyTorch data object. A tensor carries numerical data plus metadata such as shape, dtype, layout, and device placement.

4.2 Device placement

The decision of whether a tensor or model lives on CPU or CUDA. Operations normally require compatible device placement across inputs.

4.3 CUDA tensor

A PyTorch tensor whose data lives in GPU memory. Supported operations on CUDA tensors dispatch GPU-backed work internally.

4.4 Batch size

The number of items processed together. Larger batches can improve throughput but increase memory use and may worsen latency for individual requests.

4.5 Latency

The time required for one request or operation to complete. Low latency matters for interactive systems and real-time use cases.

4.6 Throughput

The amount of work completed per unit time, such as images per second or tokens per second. Throughput often improves with batching and better GPU utilization.

4.7 vLLM

A serving engine for large language model inference. It focuses on efficient batching, memory management, and OpenAI-compatible serving patterns.

4.8 KV cache

The key-value cache used during transformer inference to avoid recomputing attention state for previous tokens. It improves generation efficiency but consumes GPU memory as context and concurrency grow.

4.9 Token

A text unit processed by a language model. Inference capacity and cost are often measured in tokens per second or cost per million tokens.
