M6 - Memory Optimization

Learn how memory movement limits CUDA performance, how pinned memory and asynchronous transfers help, and how streams and shared memory can reduce idle time and global-memory pressure.

M5 PreviousM6M7 Next

Learning outcomes

  • Improve transfer behavior between host and device.
  • Understand pinned memory and asynchronous copies.
  • Use streams intentionally.

Scope

This module focuses on practical memory optimization: reducing unnecessary host-device transfers, using pinned memory and streams intentionally, overlapping work when possible, and choosing memory spaces that reduce expensive global-memory traffic.

1. Syllabus Topics

1.1 Optimization of host-device transfers

Transfer optimization begins by reducing unnecessary copies, batching work, and ensuring that data is moved only when it must change execution context. Many applications gain more from fewer transfers than from a faster kernel alone.

1.2 Use of pinned memory

Pinned or page-locked host memory improves transfer behavior by giving the runtime a host buffer that can be used efficiently for DMA-style transfers. It is most valuable when transfer cost is already significant.

Why pinned host memory matters

Ordinary host memory is pageable: the operating system may move its physical pages while managing RAM. Before a transfer, the CUDA runtime may therefore need to stage pageable data in a temporary page-locked buffer. A pinned allocation prevents those pages from being moved, allowing the GPU's DMA engine to transfer data between host memory and device memory without first staging it through another host buffer. This is why pinned memory is particularly important for efficient asynchronous host-to-device and device-to-host copies.

Pinned memory is still host memory; it is not VRAM. It consumes a limited system resource, so allocating too much can reduce overall system performance.

UVA is related but different. Unified Virtual Addressing gives the CPU and GPU a unified way to identify pointers across their address spaces. It does not make every host allocation directly accessible by the GPU, and it does not replace data transfers. When host memory is explicitly mapped for GPU access, it must be page-locked; otherwise, pinned memory is primarily being used as a reliable source or destination for DMA transfers.

1.3 Asynchronous transfers

Asynchronous copy APIs allow data movement to be enqueued without immediately blocking the host. Their real value appears when the surrounding program structure can exploit that non-blocking behavior.

1.4 Overlap between computation and data transfer

Overlap turns a program into a pipeline: while one chunk is being processed on the GPU, another chunk can be transferred. The goal is to reduce idle time and improve total throughput rather than merely changing API style.

1.5 Correct use of CUDA streams

Streams define ordering domains for CUDA operations. Commands in one stream execute in order, while independent streams may overlap depending on hardware capability and resource availability.

1.6 Choosing the most suitable memory spaces

Not all data should live in the same memory space. Read-only data, reusable block-local data, and per-thread private values each suggest different placement choices. Correct placement reduces pressure on the most expensive memory paths.

1.7 Reducing accesses to global memory

Global memory is large but costly relative to on-chip storage. Many kernel optimizations focus on reducing how often it is accessed and on increasing how much useful work is done for each access.

1.8 Using shared memory to improve performance

Shared memory enables low-latency reuse among threads of a block and is one of the main mechanisms for turning a memory-bound kernel into a more efficient one. Its use must still be balanced against occupancy and conflict behavior.

2. Guided Exercises

2.1 Transfer experiment

  • Measure transfers using regular host memory and pinned memory.
  • Explain when the observed difference justifies the extra complexity.

2.2 Overlap experiment

  • Process a large buffer in chunks using two streams.
  • Compare the sequential pipeline to the overlapped pipeline.
  • State whether the workload really achieved overlap or only changed API calls.

2.3 Coalesced and strided memory access

Now that global-memory movement and transfer behavior have been introduced, use examples/ch06/bandwidth_bottleneck to compare a coalesced copy kernel with a strided copy kernel. The two kernels move the same number of useful elements, but adjacent threads access different memory locations. Use the README instructions to measure effective bandwidth and inspect requested versus actual traffic with Nsight Compute.

  • Run the example with strides 1, 16, and 32.
  • Compare useful bandwidth, actual memory traffic, and load/store efficiency.
  • Explain why a larger stride can waste memory bandwidth even when the logical amount of work is unchanged.
  • Use Nsight Systems to distinguish kernel time from launch and synchronization overhead.
