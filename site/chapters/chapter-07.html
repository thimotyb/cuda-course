M7 - CUDA Configuration Optimization

Learn how launch configuration affects CUDA performance, how block size interacts with warps and occupancy, and how to tune kernels through measured experiments instead of fixed rules of thumb.

Learning outcomes

  • Tune thread-block size pragmatically.

  • Test configuration hypotheses systematically.

Scope

By the end of this module, you should be able to change a kernel launch configuration, predict which hardware resources might become limiting, measure several valid alternatives, and explain why the fastest configuration is specific to the kernel and GPU being tested.

1. Configuration and Launch Topics

1.1 Keeping the GPU supplied with work

A launch configuration should expose enough independent blocks to keep the available SMs busy. As a first rule, the grid should contain more blocks than the GPU has SMs, and usually many more, so that the scheduler can distribute work and create successive waves of blocks. A grid that is too small leaves hardware idle even when each individual block is efficient.

This is the grid-level view of the warp and block scheduling model introduced in M3. The practical check is the same one used in the earlier vector_add profiling exercise: distinguish a genuinely under-filled grid from a kernel that is limited by memory, instructions, or synchronization.

1.2 Choosing a block size and occupancy

Threads per block determine how threads are packed into warps and influence how many blocks can reside concurrently on an SM. Block sizes that are multiples of 32 avoid partially used warps and are a sound starting point. Values such as 128 or 256 threads per block are useful candidates, but they are not universal answers.

Occupancy is the ratio of active warps on an SM to the maximum supported active warps. It matters because resident warps provide alternatives when another warp is waiting on memory or a dependency. High occupancy is not itself the performance goal: once latency is hidden, extra occupancy may not help, and a lower-occupancy kernel may perform better if it has more registers or less spilling. Use the occupancy and scheduler observations from M3 when interpreting a launch sweep.

1.3 Balancing registers and shared memory

Each resident block consumes registers, threads, and shared memory. The first resource to reach its limit determines how many blocks and warps can be active on an SM. Increasing block size may improve parallelism but also increases the registers and shared memory allocated by the block. Increasing shared-memory use can reduce global-memory traffic, yet it can also reduce occupancy.

This is why occupancy cannot be inferred from block size alone. Inspect compiler resource reports with nvcc --ptxas-options=-v and use Nsight Compute's occupancy information. The shared-memory tiling example already studied in M4 is the relevant reference: extra shared memory is justified only when the reuse it creates outweighs the occupancy and synchronization cost.

1.4 Concurrent kernels and independent work

Separate kernels can execute concurrently when they are launched in different non-default streams, the device reports support through cudaDeviceProp.concurrentKernels, and enough execution resources remain for both kernels. Concurrent launches are useful when each kernel is too small to fill the GPU by itself or when independent work is available. They are not useful when one kernel already saturates the limiting compute or memory resource.

The same stream-ordering rules used for copy-and-compute overlap apply here: operations in one stream are ordered, while operations in different streams may overlap only when dependencies and hardware resources allow it. Compare this concept with the staged stream experiment in examples/ch06/async_overlap, which demonstrates independent work and verifies the result in Nsight Systems.

1.5 A measured configuration workflow

Configuration tuning is an experiment. Start with a correct baseline, choose several valid block sizes and grid sizes, warm up the CUDA context, measure repeated runs, and record the GPU and compiler configuration. Keep the input and algorithm unchanged while sweeping one variable at a time. Reject configurations that fail correctness checks or exceed thread, register, or shared-memory limits.

Interpret the winning configuration together with profiler evidence. Use the CPU and GPU timing separation from M5, the memory-access and bandwidth measurements from M6, and Nsight Compute's occupancy, throughput, and stall metrics. The result should explain which resource improved and why the measured end-to-end or kernel time changed.
