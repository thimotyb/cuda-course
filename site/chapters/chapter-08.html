Scope

This module shows how the CUDA ideas from the previous modules appear in everyday PyTorch code: device discovery, tensor placement, model placement, memory lifetime, synchronization, and measurement. The focus is not on writing custom kernels, but on understanding what PyTorch asks the GPU to do and how to avoid misleading benchmarks or accidental CPU/GPU transfers.

1. PyTorch CUDA Workflow

1.1 Introduction to GPU support in PyTorch

PyTorch lets a Python program use a CUDA-capable GPU without asking the programmer to write an explicit kernel launch for every operation. The central object is still the tensor. A tensor has a shape, a data type, and a device. When the device is the CPU, tensor operations run through CPU implementations. When the device is CUDA, PyTorch dispatches supported operations to GPU implementations and stores the tensor data in GPU memory.

This high-level interface does not remove the CUDA execution model; it hides most of the ceremony. The same boundaries remain: the Python process runs on the host, CUDA tensors live in device memory, operations are submitted to the GPU, and synchronization is required when the CPU needs a completed result. A line such as y = x @ w may look like ordinary Python, but if x and w are CUDA tensors, the real work is scheduled on the GPU by PyTorch and its backend libraries.

The first practical rule is that device placement must be explicit and consistent. By default, tensors are commonly created on the CPU unless a device is specified or a default device policy is active. A program can create tensors directly on CUDA with a device argument, or move existing tensors with methods such as .to("cuda"). Operations normally expect their input tensors to be on compatible devices; mixing CPU tensors and CUDA tensors in the same operation is a common beginner error because PyTorch cannot silently guess which memory space should own the computation.

The second rule is that GPU execution is useful only when the workload is large enough or repeated enough to amortize overhead. Moving a small tensor to the GPU, launching a tiny operation, and copying the result back can be slower than staying on the CPU. Larger matrix operations, batched model inference, image pipelines, and neural-network layers are better candidates because they expose enough parallel work to use the GPU's throughput.

The third rule is that timing GPU work from Python requires care. CUDA operations are commonly asynchronous with respect to the host: Python may enqueue work and continue before the GPU has finished. A benchmark that reads the wall clock immediately after a CUDA operation can therefore measure submission time instead of execution time. Correct experiments synchronize at the right boundary or use CUDA-aware timing primitives, depending on whether the goal is end-to-end application time or device-side work.

Practical mental model

PyTorch code remains Python at the orchestration level, but CUDA tensors follow the same host/device separation studied earlier in the course. Good PyTorch GPU code keeps data on the right device, avoids unnecessary transfers, batches enough work to fill the GPU, and measures only after making the synchronization boundary explicit.

1.2 Tensors as the unit of GPU work

A PyTorch tensor is the practical object that carries data into computation. It is similar to an array or matrix, but it also records metadata that matters for GPU execution: shape, data type, layout, and device. The device attribute is the bridge to CUDA. A tensor on cpu is backed by host memory and uses CPU implementations; a tensor on cuda:0 is backed by GPU memory and can participate in CUDA-backed operations.

Tensors can be initialized directly from Python data, from NumPy arrays, from the shape and type of another tensor, or with factory functions such as torch.rand, torch.ones, and torch.zeros. For GPU work, the important decision is where the tensor is created. Creating a tensor on the CPU and then calling .to("cuda") performs a host-to-device transfer. Creating it directly with device="cuda" avoids that initial copy when the data can be generated on the GPU.

Once tensors are on CUDA, familiar tensor operations such as slicing, concatenation, element-wise arithmetic, reductions, and matrix multiplication keep producing CUDA tensors when their inputs are on the same CUDA device. This is why PyTorch code can look compact while still launching real GPU work under the hood. The operation c = a @ b is a Python expression, but with CUDA tensors it maps to GPU execution and usually to optimized backend libraries.

There is one important boundary to keep visible: Python scalar extraction and NumPy interoperability bring data back to the CPU. A call such as .item() converts a one-element tensor into a Python number, which requires the result to be available on the host. That is useful for logging, but it can also introduce synchronization and data movement if placed inside a performance-critical loop.

The runnable example examples/ch08/pytorch_cuda_tensors turns these ideas into a small comparative tensor program. It prints tensor attributes, performs basic tensor operations on cuda:0, times CUDA work with events, runs the same tensor workload on CPU and GPU, reports the observed speedup, and prints PyTorch CUDA memory usage.

1.3 Using the `torch.cuda` package

The torch.cuda package is the main PyTorch interface for CUDA-aware program control. Most tensor operations still live in the broader torch API, but torch.cuda gives the program the tools needed to ask whether CUDA is available, count visible GPUs, select or inspect a device, synchronize GPU work, measure elapsed GPU time, and observe CUDA memory behavior.

Device discovery

These commands answer the first operational questions: can this process use CUDA, how many GPUs are visible, and which GPU is selected? torch.cuda.is_available() tells whether PyTorch can use CUDA from the current environment. torch.cuda.device_count() reports how many CUDA devices are visible. torch.cuda.current_device() returns the current device index, and torch.cuda.get_device_name() or torch.cuda.get_device_properties() provide human-readable and technical information about a selected GPU.

Device selection and context

Code that may run on more than one GPU should make device choice explicit. A common template is to create torch.device("cuda:0") and use with torch.cuda.device(device): around the section that should use that selected GPU. This keeps the current CUDA device visible in the code instead of relying on hidden defaults.

Synchronization and timing

CUDA work submitted by PyTorch is often asynchronous with respect to Python, so the host program can continue before the GPU has finished. torch.cuda.synchronize() creates an explicit waiting point. torch.cuda.Event is the usual tool for timing GPU-side intervals because events are recorded on the CUDA stream and measure elapsed time on the device timeline.

Streams

A CUDA stream is an ordered queue of GPU work. PyTorch exposes torch.cuda.current_stream(), torch.cuda.default_stream(), torch.cuda.Stream(), and torch.cuda.stream(stream) for code that needs explicit control over where GPU operations are enqueued. The examples use this to show the mechanism, not to claim automatic overlap.

Memory observation

CUDA memory use is managed by PyTorch's caching allocator, so Python object lifetime and visible GPU memory are related but not identical. Functions such as torch.cuda.memory_allocated(), torch.cuda.memory_reserved(), and torch.cuda.empty_cache() help explain why memory can remain reserved for reuse even after tensors are deleted.

The runnable example examples/ch08/torch_cuda_overview demonstrates the most important commands in one place: runtime inspection, device properties, memory allocator state, stream usage, CUDA event timing, synchronization, and scalar transfer back to Python.

1.4 Verifying GPU availability

GPU availability should be treated as a startup check, not as something discovered halfway through a script. A PyTorch program can import correctly even when CUDA is not usable from the current environment. The package may be installed, but the machine might have no NVIDIA GPU, the driver might be unavailable, the process might be running inside a container or WSL environment without GPU access, or the installed PyTorch build might not include CUDA support.

For this reason, CUDA exercises should begin with a small guard clause. The recurring template is: check torch.cuda.is_available(), stop clearly if it is False, then select a device such as torch.device("cuda:0"). After that, print enough information to make the environment explicit: PyTorch version, CUDA runtime version, device count, current device, and GPU name. This turns environment problems into immediate, readable failures instead of confusing errors later in the program.

This pattern is also useful in notebooks and production scripts. In a notebook, it prevents hidden CPU fallback from invalidating a benchmark. In a training or inference script, it makes logs easier to interpret because the run records which GPU was used. In a course exercise, it gives every student the same first diagnostic step before discussing tensor placement, memory, streams, or timing.

The examples in this module use this template deliberately. examples/ch08/pytorch_cuda_tensors uses a compact require_cuda() helper before creating CUDA tensors. examples/ch08/torch_cuda_overview prints runtime information first, then stops if CUDA is unavailable, then inspects the selected device. This is the expected pattern for the remaining PyTorch GPU examples.

Template

import torch

if not torch.cuda.is_available():
    raise SystemExit("CUDA is not available to PyTorch.")

device = torch.device("cuda:0")
print(torch.__version__)
print(torch.version.cuda)
print(torch.cuda.get_device_name(device))

1.5 Moving tensors and models to the GPU

Moving work to the GPU in PyTorch is mainly a device-placement discipline. A tensor operation runs where its input tensors live. A model layer runs where its parameters live. The common rule is simple: choose a device once, then make sure every tensor and every model involved in the same computation uses that device.

Direct tensor creation on the GPU

Use it when the data can be generated by PyTorch itself, such as random inputs, zeros, ones, or intermediate buffers. This avoids creating a CPU tensor only to copy it immediately to the GPU.

device = torch.device("cuda:0")
x = torch.rand((1024, 1024), device=device)
w = torch.ones_like(x)

Moving existing data to the GPU

Use it when data starts on the CPU, for example after loading from Python lists, NumPy arrays, files, datasets, or a data loader. The .to(device) call returns a tensor on the requested device.

x_cpu = torch.tensor([[1, 2], [3, 4]], dtype=torch.float32)
x_gpu = x_cpu.to(device)

Model placement

A PyTorch module owns parameter tensors. Calling model.to(device) moves those parameters and buffers to the selected device. Input tensors must be moved to the same device before calling the model.

model = MyModel().to(device)
inputs = inputs.to(device)
outputs = model(inputs)

Defensive device checking

When debugging device errors, print or assert the device of the data and the model parameters. A common failure is a CPU input passed into a CUDA model, or a CUDA input passed into a model that still has CPU parameters.

print(inputs.device)
print(next(model.parameters()).device)
assert inputs.device == next(model.parameters()).device

The earlier tensor example already uses these patterns: it creates x_cpu from Python data, transfers it with .to(device), creates later tensors directly on cuda:0, and keeps CUDA operations on CUDA tensors. The same pattern scales from a small teaching script to model inference and training code.

1.6 Difference between CPU computation and GPU computation

The CPU and GPU have different cost models. CPU execution is usually a good default for small, branch-heavy, irregular, or latency-sensitive work. The CPU has strong single-thread performance, direct access to host memory, and no need to submit work to a separate accelerator. For a tiny tensor operation, staying on the CPU can be faster because the program avoids GPU allocation, CUDA launch overhead, runtime scheduling, and synchronization.

GPU execution becomes attractive when the useful parallel work is large enough. Matrix multiplication, convolution, batched inference, image processing, and large tensor operations expose many independent arithmetic operations. In those cases, the GPU can keep many execution lanes busy and deliver much higher throughput than the CPU. The key point is that the GPU advantage appears after the workload is large or repeated enough to amortize the fixed costs.

CPU is often the better choice when

  • The tensors are small and the total amount of arithmetic is low.
  • The operation is irregular, branch-heavy, or hard to batch.
  • The data is already on the CPU and the result is immediately needed by Python.
  • The program would move data to the GPU only for one small operation and then copy it back.

GPU is usually the better choice when

  • The tensors are large enough to expose substantial data-parallel work.
  • The same model or operation runs many times, especially with batching.
  • The data can stay on the GPU across multiple operations instead of moving back and forth.
  • The operation maps well to optimized GPU libraries, such as matrix multiplication through CUDA backend libraries.

The benchmark in exercise 2.2 demonstrates this cost model directly. The same PyTorch code runs once on CPU and once on cuda:0. At 128 x 128, the CPU may win because the fixed cost of GPU execution is comparable to or larger than the useful computation. At 2048 x 2048 and 4096 x 4096, the amount of arithmetic grows quickly, so the GPU should become more competitive and then clearly advantageous if memory capacity is sufficient.

Correct measurement matters because CUDA execution is often asynchronous with respect to Python. A GPU operation can be enqueued quickly while the actual work continues on the device. That is why the examples use CUDA events and explicit synchronization. Without that boundary, a benchmark can accidentally measure submission time instead of completed GPU execution.

The practical rule is: do not ask whether GPUs are faster in general. Ask whether this specific workload has enough parallel work, enough reuse, enough batching, and few enough transfers to make the GPU worthwhile.

1.7 Basic management of GPU memory in PyTorch

PyTorch manages CUDA memory through a caching allocator. The allocator improves performance because memory blocks can be reused instead of repeatedly asking the CUDA driver for new allocations. This is useful, but it also means GPU memory numbers must be read carefully: memory owned by live tensors and memory reserved by PyTorch for reuse are not the same measurement.

Allocated memory

torch.cuda.memory_allocated(device) reports GPU memory currently occupied by tensors and active allocations managed by PyTorch. This number usually follows live tensor pressure, but library-backed operations can also leave internal allocations visible.

Reserved memory

torch.cuda.memory_reserved(device) reports GPU memory held by PyTorch's CUDA caching allocator. Reserved memory can remain higher than allocated memory because PyTorch may keep released blocks ready for future CUDA tensor allocations.

Reserved memory is not pinned memory

Reserved CUDA memory is GPU device memory cached by PyTorch. Pinned memory is CPU host memory that has been page-locked to make host-device transfers more efficient. The names are easy to confuse, but they refer to different memory spaces and different purposes.

Cleanup and cache behavior

Deleting tensors releases their memory back to PyTorch's allocator when no references remain. Calling torch.cuda.empty_cache() releases unused cached blocks back to the CUDA driver, but it does not free memory still owned by live tensors or internal library state. It is a visibility and cache-management tool, not a substitute for fixing tensor lifetime or batch-size problems.

Peak and device-level counters

torch.cuda.max_memory_allocated() and torch.cuda.max_memory_reserved() show the peak pressure reached during a run. torch.cuda.reset_peak_memory_stats() resets those peak counters. torch.cuda.mem_get_info() reports free and total memory from the device perspective, which is useful for comparing PyTorch allocator numbers with overall GPU availability.

The runnable example examples/ch08/pytorch_cuda_memory demonstrates these counters by allocating tensors, running a matrix multiplication, deleting references, emptying the cache, and printing the memory state after each step.

2.2 PyTorch benchmark exercise

Use the tensor example as a small benchmark experiment. The program runs the same workload on CPU and on cuda:0:

mixed = (a + b) * 0.5
out = mixed @ b.T

Launch three input sizes from the repository root:

.venv/bin/python examples/ch08/pytorch_cuda_tensors/pytorch_cuda_tensors.py --size 128
.venv/bin/python examples/ch08/pytorch_cuda_tensors/pytorch_cuda_tensors.py --size 2048
.venv/bin/python examples/ch08/pytorch_cuda_tensors/pytorch_cuda_tensors.py --size 4096
  • Record CPU workload time, CUDA workload time, and CUDA speedup over CPU for each size.
  • For 128 x 128, the CPU can be faster. On the course reference machine, this produced CPU workload time: 7.237 ms and CUDA workload time: 14.856 ms. The GPU is not weak here; the workload is simply too small to amortize CUDA setup, scheduling, launch, allocation, and synchronization costs.
  • For 2048 x 2048, the arithmetic work grows enough that the GPU should usually become more competitive. The launch and synchronization overheads are still present, but they are spread over a much larger matrix multiplication.
  • For 4096 x 4096, the operation exposes much more parallel work. If the GPU has enough memory, this is the case where CUDA should normally show its throughput advantage clearly.
  • Explain the result using the full execution cost, not only the hardware peak. The CPU path measures CPU allocation and CPU computation; the CUDA path measures CUDA allocation, GPU work submission, GPU computation, and synchronization. The GPU becomes attractive when the useful parallel work is large enough to amortize those fixed costs.
  • Synchronize before reading GPU timing, or use CUDA events as the example does. Without a synchronization boundary, Python may measure only the time needed to enqueue work, not the time needed for the GPU to finish it.
