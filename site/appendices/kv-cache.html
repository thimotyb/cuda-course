Appendix - Queries, Keys, Values, Prefill, and Decode

A slower explanation of the attention mechanism behind the KV cache used during transformer inference.

Back to M9KV Cache Appendix

1. The Mental Model

1.1 Query, Key, and Value

In self-attention, every token is projected into three different vectors. The query represents what the current token is looking for. The key represents how a token can be matched by other tokens. The value carries the information that will be mixed into the output if that token receives attention.

Query = what am I looking for?
Key   = how can I be found?
Value = what information do I provide?

The model compares a query with keys to decide where to look. Then it uses the resulting attention weights to combine values.

Query + Keys -> attention weights -> weighted sum of Values

1.2 Similarity to vector search

The idea is close to retrieval with embeddings. In a vector database, a question embedding is compared with stored chunk embeddings to decide which chunks are relevant. In self-attention, the query vector of the current token is compared with key vectors from previous tokens to decide which previous token states are relevant.

Vector search or RAGSelf-attention
Question embeddingQuery vector
Stored chunk embeddingsKey vectors
Retrieved text chunksValue vectors mixed into the hidden state
External database lookupInternal operation inside every transformer layer and attention head

The analogy is useful, but it is not exact. Self-attention does not retrieve documents. It combines internal token representations inside the model.

4. Why It Is Called KV Cache

4.1 What is reused

The cache stores keys and values because old keys and values remain useful for future decode steps. The query is different at every step because it comes from the current token.

Reusable from previous tokens: K and V
New at each decode step:      Q

This is why the optimization is called a KV cache, not a QKV cache.

4.2 Performance consequence

Without a KV cache, the model would repeatedly recompute key and value state for the whole prefix every time it generates a token. With the cache, it avoids that repeated compute. The trade-off is memory: cached K and V tensors occupy GPU memory for every layer, attention head, token, and active sequence.

More context or more concurrent requests
-> more cached K/V tensors
-> more GPU memory use
-> more KV-cache reads during decode

This is why vLLM tuning connects directly to CUDA memory behavior. Larger batches can improve GPU utilization, but larger or longer active sequences also increase KV-cache pressure.

5. What To Look For In Perfetto

5.1 Timeline shape

In a trace, prefill often appears as a smaller number of larger execution ranges because the prompt is processed as a chunk. Decode appears as many repeated ranges because generation advances one token at a time.

Prefill: prompt tokens processed together
Decode:  token 1, token 2, token 3, ...

For decode-heavy workloads, the GPU may spend substantial time reading model weights and KV-cache data. That can make the workload memory-bound even when each single decode step is not mathematically large.
